## README 需處理的具體位置

計劃撰寫期間確認的落差：

1. **第 66 行**：「多頁 TIFF、高位深與浮點圖片會明確拒絕；普通圖片轉成 RGB，不保存 alpha、GIS 或其他 metadata。」
   - 「高位深」在 phase-02 之後才對彩色成立 —— 確認敘述與實際涵蓋範圍相符。
   - 「不保存 metadata」是輸出端承諾，**不涵蓋輸入端幾何**。需補上：依 EXIF 方向校正像素後輸出，不保留方向標記。避免未來讀者再次把兩件事混為一談。
   - 若 phase-02 未能驗證 float 彩色 TIFF，「浮點」的說法需相應收斂。
2. **第 64 行**：`input/DJI_001.JPG` 範例。這正是帶方向標記的典型來源；確認修正後此範例的敘述成立。
3. **新增限制記錄**（可放在「驗證紀錄」或限制段落）：
   - 未壓縮 TIFF ＋ Orientation 5–8 ＋ mode `L`／`P`／`RGBA`／`CMYK` 時 Pillow 的 size／資料不一致，屬上游缺陷，本次未處理。
   - 輸出 PNG 權限為 `0600`（原子寫入副作用），本次未改。
   - 任何 phase-01／02 記為未驗證的項目。

**不得把未執行的檢查寫成已確認可用**（`AGENTS.md`「評估、驗證與回報」）。

## 實作與驗證

### Preflight

- 確認前兩階段為 `Complete`，`git status` 乾淨。
- 讀 `../build-log.md` 實際證據，而非本計劃的預期敘述；README 只能寫已被觀察的內容。

### 文件修改

依「README 需處理的具體位置」逐項調整，語言與既有 README 一致（繁體中文、既有術語）。只改必要句子，不重寫章節。

### 驗證

- **完整 suite：**
  ~~~bash
  .venv/bin/python -m unittest discover -s tests -v
  ~~~
  記錄實際測試數（既有 29 加本次新增）與通過狀況，無 skipped。
- **真實小批次 CLI：** 在暫存輸入資料夾放入
  1. 一張帶 Orientation 5–8 的真實照片或等效 fixture，
  2. 一張 16-bit RGB PNG，
  3. 一張正常 8-bit RGB PNG（可用 `test-data/` 既有真實裁切的副本，不動原檔）。

  執行真正的 `python -m drone_sr --input ... --output ...`，確認：方向圖輸出朝向正確、16-bit 記為 Failed 並附原因、正常圖成功、`Processed: 2`／`Failed: 1`、退出碼 1、三張來源檔雜湊不變。
- **README 逐條對照：** 將修改後的每句 I/O 敘述對應到 `../build-log.md` 的具體證據。
- **失敗行為：** 對照發現敘述無證據支持時，改敘述或回到對應階段補證據，不得保留無證據的宣稱。

## 可靠性、安全與復原

- 純文件變更加驗收；`AGENTS.md` 規定純文件變更只需確認內容與差異。本階段的模型執行來自驗收需求，不是文件變更本身。
- 真實批次使用既有 `models/model.pth`（Compact），小尺寸輸入，預期遠低於十分鐘。超出則依 `PLANS.md` 先說明成本。
- 不修改 `input/`、`output/`、`test-data/` 既有內容；驗收使用暫存資料夾與副本。
