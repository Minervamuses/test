# evaluation — 目標

## 背景與問題

本專案目前能把資料夾裡的圖片跑完 4× SR 並輸出 PNG，但沒有任何量化證據能回答使用者真正在意的問題：

> 當一張低解析度的圖進來，走本專案的 SR，畫質是否真的贏過一般的放大手段（bicubic）？

`README.md:11` 明列「不計算 PSNR／SSIM，也不做模型或畫質排名」，`README.md:156` 也記錄了理由：手上沒有「配對且對齊的高解析度真值」。本計劃用**合成退化**補上這個缺口：拿高解析原圖當真值，自己降採樣造出低解析輸入，再用兩種方式放大回去，與原圖比對。

真值是自己造的，所以整個比較的可信度完全取決於退化流程是否固定、對稱、且沒有偷吃步。本計劃的主要工程風險不是「算不出數字」，而是「算出看起來合理但其實不對等的數字」。

## 期望結果

- 一份可重複執行的評估工具，輸入一批高解析原圖，輸出逐張與平均的 PSNR／SSIM／LPIPS，同時涵蓋 SR 線與 bicubic 線。
- 每次執行留下獨立、不覆蓋舊紀錄的成績檔，含完整的執行環境與參數，讓數字之後仍可被追溯與重現。
- 使用者能據此對「SR 是否贏過一般放大」給出有證據的答案，並知道這個答案在什麼前提下成立。
- 既有 SR pipeline 的程式、測試、輸入與輸出完全不受影響。

- [ ] 兩條線的輸入都可觀察地來自**磁碟上同一個低解析 PNG 檔**；bicubic 線沒有任何路徑能直接碰到原圖。

## 固定的退化與放大契約

以下為本計劃的核心不變式。任何一條改變，先前所有數字都不可再與新數字並列比較，必須註記為不同批次。

1. **原圖讀取：** Pillow `Image.open` → `ImageOps.exif_transpose` → `convert("RGB")`。多影格來源（例如 DJI 的 MPO JPEG）取第一影格。每通道超過 8-bit 的來源直接略過並記錄原因，不做位深轉換。
2. **對齊裁切（mod-crop）：** 把原圖裁到寬高皆為 4 的倍數（自右／下各裁至多 3 px）。**裁切後的原圖才是本次比較的真值**，逐張記錄原始尺寸、裁切後尺寸與裁掉的像素數。
   - 理由：若寬高不是 4 的倍數，降採樣再放大回來的尺寸對不上原圖，唯一的替代做法是把結果重新縮放到原圖尺寸，那會引入使用者明令禁止的額外失真。裁切不改動任何保留下來的像素。
3. **降採樣：** `cropped.resize((W // 4, H // 4), resample=Image.Resampling.BICUBIC)`，寫成 PNG。
4. **兩條放大線的輸入都是步驟 3 寫到磁碟的那個 LR PNG 檔**，不是記憶體裡的原圖，也不是原圖的任何衍生物。
   - **bicubic 線：** 重新 `Image.open(lr_png)` → `resize((W, H), resample=Image.Resampling.BICUBIC)` → PNG。
   - **SR 線：** 未修改的 `drone_sr.read_image(lr_png)` → `upscale(...)` → `write_png(...)`。
5. **全程 PNG。** 除了步驟 1 對來源檔的那一次解碼之外，不得有第二次有損編碼、第二次縮放或任何色彩空間轉換。

## 固定的度量約定

1. **色彩空間：** RGB 三通道、8-bit、`data_range = 255`。不使用 Y 通道。兩條線套用完全相同的約定，比較才對等；報告必須寫明採用的是 RGB 而非論文常見的 Y 通道，數值不可直接與論文對照。
2. **PSNR：** `10 * log10(255 ** 2 / MSE)`。`MSE == 0` 時記為 `inf`，該張排除於 PSNR 平均之外，SSIM／LPIPS 照常納入，並在報告標明。
3. **SSIM：** Gaussian window 11×11、σ=1.5、K1=0.01、K2=0.03；三通道各自計算後取平均。
4. **LPIPS：** `lpips` 套件、`net='alex'`、輸入正規化到 `[-1, 1]`、RGB。記錄套件版本與權重檔的來源與 SHA-256。
5. **平均：** 只對「SR 線與 bicubic 線都成功量到」的圖片取算術平均，並明確記錄納入張數、排除張數與排除原因。任一線失敗的圖片兩邊都不計入。
6. **執行裝置與決定性：** 單次執行內，SR 線與三個度量所用的裝置固定，並寫進報告標頭。GPU 執行必須設 `torch.backends.cudnn.benchmark = False`，且決定性檢查要在**實際執行的那個裝置上**通過，不得以 CPU 的決定性結果代表 GPU 路徑。CPU 與 GPU 的浮點結果不保證相同（TF32、cuDNN 演算法選擇），兩者的數字不可並列比較，須註記為不同批次。bicubic 線恆為 Pillow 的 CPU 實作，不受裝置選擇影響。

- **限制：** 新依賴只授權 `lpips`，且只記錄在 `evaluation/requirements.txt`。
  - **權威：** 使用者於 2026-09-18 的決定。
  - **影響：** PSNR 與 SSIM 必須自行以 torch 實作，不得改裝 `scikit-image` 或 `torchmetrics`；`pyproject.toml` 與 `requirements-wsl.txt` 不得更動。
- **限制：** 原圖來源接受 `.png` 與 `.jpg`／`.jpeg`。
  - **權威：** 使用者於 2026-09-18 的決定，取代原先「只收 PNG」的要求。
  - **影響：** 若來源是 JPEG，真值本身就是已經有損的 JPEG 解碼結果。這不影響兩條線的對等性（兩邊比的是同一個真值），但報告必須標明真值的來源格式。
- **限制：** 成績檔為 Markdown。
  - **權威：** 使用者於 2026-09-18 的決定。
  - **影響：** 逐張表格與平均寫在同一份 `report.md`，執行環境與參數一併放在該檔標頭。
- **限制：** 本機 GPU 是 RTX 5070 Ti Laptop（12227 MiB VRAM、compute capability 12.0、driver 591.74）。**GPU 在使用者的一般 WSL shell 可用，但在 coding agent 的沙箱 session 內被作業系統擋住。**
  - **權威：** `AGENTS.md`「本機資源限制與提前告知」；2026-09-19 使用者 shell 實測 `torch.cuda.is_available()` 為 `True`、裝置名稱 `NVIDIA GeForce RTX 5070 Ti Laptop GPU`；同日沙箱 session 內實測為 `False`（`nvidia-smi` 回報 `GPU access blocked by the operating system`、`/dev/dxg` 不存在、`torch.cuda.device_count()` 為 0，但 `torch.version.cuda` 為 12.8，wheel 本身帶 CUDA）。2026-09-18 記錄的 `False` 是沙箱環境的結果，**不是本機沒有 GPU**。
  - **影響：** 交付裝置是 GPU。實作與便宜的小尺寸檢查可在沙箱 session 內做；**所有真實資料的執行與所有資源量測（耗時、峰值 RSS、峰值 VRAM、device）必須在使用者自己的 shell 執行**，否則量到的是 CPU 數字而非交付環境的數字。`AGENTS.md` 禁止「默默改用 CPU 長跑」，因此沙箱內若因看不到 GPU 而落到 CPU，必須明說並標為非交付環境的觀察，不得當成 GPU 路徑的證據。
  - **影響：** 必須以實測決定樣本規模，全量執行需另外取得同意。
- **限制：** 適用的 `AGENTS.md` 始終權威，本計劃不取代它，也不得修改它。

## 已知會影響結論解讀的性質

這一節不是待辦，是避免誤讀結果的前提，實作時不得從報告中省略。

- 本計劃的退化是**純 bicubic 降採樣**，而 `realesr-general-x4v3` 是以真實世界複合退化（模糊、雜訊、壓縮）訓練的 GAN 模型。在乾淨的 bicubic 基準上，GAN 類 SR 常見的結果是 **PSNR／SSIM 輸給 bicubic，但 LPIPS 明顯勝出**。若出現這個組合，那是評估設定的已知性質，不是實作錯誤。
- 因此「是否打贏一般放大手段」必須三個指標分別下結論，並在報告中說明 PSNR／SSIM 衡量的是逐像素保真度、LPIPS 衡量的是感知相似度。不得只用 PSNR 判勝負，也不得因為分數不如預期就回頭調整退化流程來「修好」數字。
- 報告只描述本次退化設定下的結果，不可外推成「本專案在真實低解析影像上的畫質排名」。

## 未解問題與使用者決策

- **未解：** `input/` 目前是 738 張 4056×3040 的 DJI JPEG（MPO，`n_frames = 2`）與 0 張 PNG，全量跑一次的成本尚未實測。
  - **為何重要：** 決定驗收樣本規模，以及是否需要額外授權。
  - **解決方式：** phase-03 量測單張端到端耗時與峰值 RSS，phase-05 據此估算全量成本並回報；全量執行需使用者另外同意。
- **未解：** SSIM 自行實作後，是否有可用的獨立實作能做一次交叉核對。
  - **為何重要：** 自行實作的 SSIM 若有錯（window 正規化、邊界處理、通道平均方式），數字會看起來合理但系統性偏差。
  - **解決方式：** phase-02 以性質檢查（同圖 = 1.0、單調性、決定性）為必要證據；交叉核對若不可得，記為限制，不得略過不提。
- **未解：** LPIPS 在 4056×3040 全尺寸影像上的耗時與記憶體需求未知。交付裝置為 GPU 後，主要瓶頸由 CPU 耗時改為 **12227 MiB VRAM**：LPIPS 的 AlexNet activations 與 SR 分塊推論若在同一程序內未及時釋放，有 OOM 風險。
  - **為何重要：** 可能成為比 SR 推論本身更大的瓶頸，甚至觸發 OOM。
  - **解決方式：** phase-02 先以一張真實尺寸影像在**交付裝置（使用者 shell 的 GPU）**上量測耗時、峰值 RSS 與峰值 VRAM，結果寫入 build-log；SR 與 LPIPS 之間明確釋放張量並呼叫 `torch.cuda.empty_cache()`。若不可行，停止並回報，不得自行改成縮圖後再算 LPIPS（那會改變度量定義）。CPU 備援路徑存在，但其數字屬於不同批次（見「固定的度量約定」第 6 條）。
