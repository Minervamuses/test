# Phase 04 — 執行器、run 目錄與逐張＋平均報告

## 來源輸入

- `../GOALS.md`（成功條件、固定度量約定第 5 條「平均」、必須保留的行為與不變式）
- `../PLANS.md`
- phase-01、02、03 的產出與 `../build-log.md` 的實測數字

## 目標

一個命令跑完整個評估：探索原圖 → 降採樣 → 雙線放大 → 三個度量 → 寫出**一份** `report.md`，內含逐張成績與最後的平均。每次執行建立一個新的 `evaluation/runs/<timestamp>/`，絕不寫入或覆蓋既有 run。

## 範圍內

- CLI 入口（例如 `python -m evaluation.run` 或 `python evaluation/run_evaluation.py`，實作決定）。
- 參數：輸入資料夾（預設 `input/`）、取樣上限、隨機或依序取樣的選擇。**預設不跑全量。**
- run 目錄命名與防覆蓋：`evaluation/runs/<YYYYMMDD-HHMMSS>/`；目錄已存在時加序號或直接失敗，兩者擇一並寫進文件，但**絕不寫進既有目錄**。
- 逐張失敗隔離：單張任一環節失敗時記錄檔名與原因，繼續下一張。
- 平均：只涵蓋兩條線都成功量到的圖片；記錄納入張數、排除張數與每個排除原因。
- `report.md` 的完整內容（見下）。
- 結束時的摘要輸出與退出碼。

## 非目標

- 不改變 phase-01／02／03 已確立的退化契約與度量約定。
- 不加畫質優化、不加模型選項、不加圖表或視覺化。
- 不做 CSV／JSON 輸出（使用者已選定 Markdown 單一檔案）。
- 不跑全量 738 張（需另外授權，見 phase-05）。

## 依賴與前提

- 依賴階段：01、02、03 全部 `Complete`。
- **不得**在本階段才第一次驗證度量或退化是否正確。若前面階段的證據不足，先回去補，否則數字出問題時無法判斷是哪一層。
- **Unresolved：** 樣本上限的預設值。由 phase-02／03 在**交付裝置（GPU）**上的實測耗時決定，目標是預設執行落在十分鐘以內；決定後寫進 build-log 與報告標頭。CPU 與 GPU 的合理上限相差約一個量級（見 `../PLANS.md`「資源」），因此預設值必須綁在實測到它的裝置上，報告標頭要寫明該預設值假設的裝置。

## 預期影響的元件

- 新增：`evaluation/` 的執行器與報告產生器。
- 寫入：`evaluation/runs/<timestamp>/`（`report.md` 與各線影像）。
- 不需變更：`.gitignore` 的 `/evaluation/runs/` 規則已於 2026-09-18 套用（`.gitignore:15`），run 產物不會進入版本控制。

## 授權與停止條件

- 常規：在 `evaluation/` 內實作、跑有界小樣本。
- **停止：** 需要全量執行或預估超過約十分鐘的執行。
- **停止：** 為了讓平均「好看」而想改變納入規則（例如排除表現差的圖片）。納入規則由 `GOALS.md` 固定。

## `report.md` 必須包含

### 標頭（讓數字日後可被追溯）

- 執行時間（含時區）與 run 目錄路徑。
- `git rev-parse HEAD` 與 worktree 是否乾淨。
- 原圖來源資料夾、探索規則、取樣方式與上限、實際張數。
- 退化契約：降採樣與放大演算法（`Image.Resampling.BICUBIC`）、倍率 4、Pillow 版本、mod-crop 規則。
- SR 設定：`models/model.pth` 的實際目標檔名與 SHA-256、descriptor 架構與 scale、device、tile 設定。
- 度量約定：RGB、`data_range = 255`、SSIM 參數、LPIPS 套件版本與 `net`、權重雜湊。**必須寫明採用 RGB 而非 Y 通道，數值不可直接與論文對照。**
- 執行裝置：SR 線與三個度量各自所用的 device、`cudnn.benchmark` 設定，以及本次數字是否可與先前批次並列比較（依 `../GOALS.md`「固定的度量約定」第 6 條，跨裝置不可並列）。
- 解讀前提：`GOALS.md`「已知會影響結論解讀的性質」那一段的重點（純 bicubic 退化 vs GAN 模型的已知傾向），不得省略。

### 逐張表

每張一列：檔名、原始尺寸、裁切後尺寸（真值）、LR 尺寸、SR 的 PSNR／SSIM／LPIPS、bicubic 的 PSNR／SSIM／LPIPS、每個指標的勝方。

### 平均

- 三個指標在兩條線上的算術平均。
- 納入張數、排除張數。
- 每個指標各自的勝方，以及差距。

### 失敗與排除清單

- 檔名、失敗環節、原因。
- 被略過的來源（高位深、無法解碼等）與原因。

## 實作與驗證計劃

### Preflight

- 確認 phase-01／02/03 在 `build-log.md` 皆為 `Complete` 且有證據。
- 記錄 `input/`、`output/`、`src/` 的狀態供結束比對。

### Red

1. **不覆蓋舊紀錄：** 連跑兩次，產生兩個不同的 run 目錄；第一次的 `report.md` 與影像內容、mtime 未變。
2. **同一時間戳：** 人為在同一秒觸發兩次（或直接預建同名目錄），確認採用的防覆蓋策略生效，既有目錄內容不變。
3. **平均的納入規則：** 用一個會讓某張圖在 SR 線失敗的 fixture，確認該張在兩條線的平均中都被排除，且出現在失敗清單，報告仍然寫出。
4. **PSNR `inf`：** 用一張「LR 放大後恰好等於真值」的人造案例（或直接對度量層注入相同影像），確認 PSNR 記為 `inf`、排除於 PSNR 平均、仍納入 SSIM／LPIPS 平均，且報告標明。
5. **報告完整性：** 報告包含標頭所有必填欄位、逐張列數等於成功張數、平均列存在。

### Green

實作滿足上述檢查所需的最小行為。

### Refactor

不預期。若調整報告結構，重跑第 5 項檢查。

### Verification

- **聚焦：** 上述五項檢查通過。
- **較廣（真實資料）：** 跑一次 3–5 張真實圖片的小樣本，人工讀一次 `report.md`，確認每個欄位都有值、沒有 `None`／`nan`／空白。
- **不變式：** `output/`、`input/`、`src/`、`tests/`、manifest 未變動；所有寫入都在 `evaluation/runs/<timestamp>/` 之下。
- **失敗行為：** 任一檢查失敗，本階段維持 `In progress`，phase-05 不得開始。

## 可靠性、安全與復原

- **不覆蓋舊紀錄是使用者的明確需求，屬於資料完整性問題**，因此第 1、2 項檢查是必要證據。
- 執行中斷時，該 run 目錄會留下部分產物。報告產生應在能寫出時就寫出（含已完成張數與中斷說明），讓部分結果仍可追溯；不要為了「完整性」而在中斷時什麼都不留。
- 清理：本計劃不自動刪除舊 run。磁碟成長由使用者決定何時清理，phase-05 的文件要說明每個 run 的大致體積。

## 驗收條件

- [ ] 連跑兩次產生兩個獨立 run 目錄，先前紀錄內容與 mtime 未變。
- [ ] 同名目錄情境下的防覆蓋策略已驗證，既有內容不變。
- [ ] 單張失敗被隔離、記入失敗清單、排除於兩條線的平均，報告仍寫出。
- [ ] PSNR `inf` 的處理符合 `GOALS.md` 約定並在報告標明。
- [ ] 報告標頭所有必填欄位都有實際值，含解讀前提那一段。
- [ ] 逐張表與平均列都存在，納入／排除張數明確。
- [ ] 所有寫入都在 `evaluation/runs/<timestamp>/` 之下；`output/`、`input/`、`src/`、`tests/` 未變動。

## Commit 切點

實作段建議四顆。報告與平均分開的理由：數字可疑時，要能分辨是「算錯」還是「呈現錯」。

1. `feat: allocate evaluation run directories without overwriting` — 命名與防覆蓋。body 記連跑兩次的兩個目錄路徑，以及第一次未被更動的比對方式。
2. `feat: run both upscale lines over a bounded sample` — 批次執行、取樣參數、逐張失敗隔離。body 記採用的樣本上限預設值與理由。
3. `feat: average only images measured on both lines` — 納入規則與 PSNR `inf` 的處理。body 記用來驗證的 fixture 情境與結果。
4. `feat: write the per-image and average markdown report` — `report.md` 的標頭、逐張表、平均、失敗清單。body 記真實小樣本的報告路徑。

## 要記錄的證據

- 兩次執行的 run 目錄路徑，以及「第一次未被更動」的比對方式與結果。
- 小樣本執行的實際耗時與產物體積。
- 採用的樣本上限預設值與理由。
- 採用的防覆蓋策略（加序號或失敗）。
